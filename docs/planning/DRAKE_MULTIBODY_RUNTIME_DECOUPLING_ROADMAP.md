# Drake 多体运行时脱耦路书

本文件是 ORVD 当前唯一的实施路书。它把项目拆成 18 个子目标、50 个原子 Goal。
每次 Goal 模式只执行其中一个 Goal；不得在执行过程中重新规划整条路线或顺手扩展范围。

## 当前状态

- 工作分支：`main`
- 当前阶段：提供模型中立拓扑门面
- 当前 Goal：`G30`
- 产品代码状态：刚性树已成内部产品目标 `orvd_rigid_multibody_tree`，其对象集合与全部落位翻译单元动态一致且各一次；编译前沿无缺口，`systems::`、`CacheEntry`、`DependencyTicket`、`MultibodyTreeSystem` 全树归零。第一方运行时已落地状态布局、类型化参数存储、五个版本源、类型化缓存槽、惰性求值与十一个具名缓存槽的真实绑定；最小建模程序可最终化模型、创建独立求值上下文并求值运动学。G29 已建立零 Drake 公共类型的程序化建模门面，最终化与稳定查询归 G30，安装与导出归 G46。
- 已验证平台：Ubuntu 24.04 + GCC 13。Clang、MSVC 与 Windows 尚未实测，不提前宣称
  已跨平台；正式资格门仍是 G46
- 仓库外探针：只作一次性研究输入，不直接复制进产品

## 不再讨论的前提

- 采用方案 B：先 vendor Drake 刚性多体树与拓扑，再逐步替换。
- 产品只支持 `double`；运行期不保留自动微分或符号标量。
- 最终产品不链接 `libdrake`。
- Eigen、fmt、SUNDIALS CVODE、Ceres 是允许的外置第三方。
- 保留模型中立的系统组装层；首个推进后端是 CVODE。
- GZ18 在模型中立运行时稳定后接入，不参与底层接口塑形。
- 条件良好的 `double` 跨实现连续量默认采用 `1e-8` 相对误差；近零量使用按单位声明的绝对
  限；旋转使用 `1e-8 rad` 的 SO(3) 测地角。代数恒等式、有限差分、迭代求解和病态问题
  按各自误差来源另定判据，不把 `1e-8` 用作万能阈值。
- 不保存数值金标、输出快照、文件哈希或平台结果档案。
- 可信本地生成器产生的探针输入采用宽松解析；只检查实际使用字段能否解析及维数是否正确。
- 不提供旧名称、旧格式、旧接口或错误实现的回退兼容。

## 仓库外原型的处理规则

仓库外已存在可运行的启动器、参考发射器与缓存探针。它们**既不整文件迁入，也不盲目逐字重写**：

1. 先由 Goal 确定主线的长期接口，再逐函数审查仓外实现。
2. 只有脱离旧协议、脱离硬编码场景、脱离探针目录结构的**纯算法片段**可以选择性采用，并按第一方工程规范重构。
3. 现有启动器把场景定义、线协议、比较判定和进程管理混在一个文件里，不得整体复制：G06 吸收场景语义，G07 重建比较职责，G08 吸收缓存事实。
4. 主线测试承接必要知识后，仓库外探针整体删除，不归档、不留压缩包或软链接。

## Goal 模式规则

每个 Goal 必须满足以下格式：

```text
Goal GNN — <明确的功能名称>

前置 Goal：
唯一产物：
允许修改：
明确不做：

完成门：
1. <可执行、可判定>
2. <可执行、可判定>
3. <可选第三项>
```

执行纪律：

1. 一个 Goal 只产生一个逻辑产物；直接测试和必要说明随产物一起完成。
2. 默认在同一工作分支连续推进，一 Goal 一个聚焦提交；不为 50 个 Goal 创建 50 个分支。
3. 每次开始前读取本路书中的 Goal 定义和直接前置产物，不重新审议已定路线。
4. 完成门全部通过才标记完成；失败就在当前 Goal 内修复，不用兼容层绕过。
5. 若发现必须改变已接受架构，停止当前 Goal，先单独形成明确的新决策。
6. 构建产物、日志、临时观测、性能输出、金标和哈希不进入 Git。
7. 探索性测试用完即可删除；保护核心语义的短测试长期保留。

  - 产物：读取位置与速度运动学缓存 `serial_number` 与 `is_out_of_date` 的模型中立探针。
  - 完成门：重复求值后两者保持新鲜且序号均不变；改 `v` 或改 `q` 后两者均过期且序号在重求值前不变——Drake 当前只能整段取用可变 `q/v`（源码 TODO 明示），共同失效是参考实现的保守现状，不是 ORVD 的永久要求；过期后按需分别重算：先求位置仅位置序号严格递增、速度仍过期，再求速度后恢复新鲜；修改一个 Context 不影响另一个；任一语义不符返回非零。序号只判「不变」或「严格递增」，不锁定绝对值、缓存索引或恰好加一。

    施力并使用工作区，不把外层 system 的声明包络复制进长期缓存。
    参数按实际读取拆成有证据的类别：改一个刚体质量只影响惯量一支及其传递依赖，

    「Create more granular parameter tickets」的 TODO。
    另定：joint damping 缓存删除、阻尼力在 G35 直接计算；system Jacobian 首版直接计算，
    不预分配缓存；重力向量归为最终化后不可变的模型数据，不建缓存版本。

  - 完成门：一次成功修改只推进对应版本一次，失败的修改保持状态与版本均不变；没有缓存
    消费者的状态不为对称性凭空获得版本源，热路径不复制整块状态。
  - 隔离门：两个状态实例可引用同一不可变最终模型，但不共享状态或版本；修改其中一个
    不会改变另一个。G27 组合缓存后继续保持同样的上下文隔离。
  - 实测结论：版本源恰好五个——广义位置、广义速度、全部固定坐标系位姿、全部刚体惯量、
    全部执行器转子惯量与传动比。三类参数在 G20 契约中的长期缓存消费者集合两两不同
    ({3,4,6,7,8,9,10,11,12,13}、{3,6,7,10,11,13}、{1,11,13}),因此不能合并;
    关节阻尼、转动弹簧与线性衬套无缓存消费者,不获得版本源。参数按类别整体版本化,
    不按元素:相关缓存都是整模型缓存,没有能只对一个 body、frame 或 actuator 失效的消费者。
    `MultibodyStateVersion` 只比相等、只产生后继,不隐式转整数、不做算术、不排序;成功
    提交即推进,不做值比较——少推进会静默给出陈旧答案,多推进只是白算一次且被重算计数

    因此计数耗尽不会留下「数据已写、版本未推进」,后续单线程求值也不会在旧数据仍在原处时
    看见新版本；这不是并发同步机制。
    版本计数耗尽分支经公开 setter 理论可达,但常规测试无法实际覆盖:须先完成
    2⁶⁴−1 次成功写入再发起一次；不为这一条直白分支增加生产测试钩子。
  - 判别力：常驻测试覆盖五类成功写、同值重写、失败原子性、三类无版本参数和双实例隔离；
    实施时的错误类别、双推进、提前推进与遗漏推进扰动均会使测试失败，扰动本身不入仓。

    对同一求值器验证。提交只允许出现在成功重算之后,该调用顺序由 G25 求值器封装并测试,

  - 判别力：常驻测试覆盖冷槽拒读、相关与无关版本变化、重算前作废、放弃重算、槽与状态隔离、
    预分配值地址稳定及构造、复制和移动边界；实施期扰动不进入仓库或长期路线。

- [x] **G24 — 验证版本依赖与新鲜度机制**
  - 产物：每个缓存槽保存其真实源版本快照，并直接比较 q、v 或相关参数版本；不建立 ticket
    图、通用依赖图或每参数机械分裂的版本体系。
  - 正确性门：用合成的类型化值与计算器验证同版本热读、依赖版本变化后过期、无关版本
    变化不重算及重算次数；本 Goal 不声称尚未接入的真实 tree 缓存已经正确。
  - 完成门：机制能表达 G20 的语义根版本依赖集合，不把 Drake 的 q/v 共同失效当成永久契约；
    真实位置、速度与惯量的冷热上下文对照留在 G27。
  - 实测结论：G20 契约保留的 11 个缓存,其语义根依赖收敛为 **8 种不同的子集**;逐子集建槽,
    对五个源各跑一格,共 **40 格**。预期矩阵**逐行手写**(五个具名布尔字段,并注明契约缓存
    编号 #1、#3、#4/#9、#6/#7、#8/#12、#10、#11、#13),不从 `Sources...` 反推——槽用
    `Sources...` 算新鲜度,若预期也这么算,则无论声明对错都会一致,而声明正是本 Goal 要验的
    东西。每格用全新的 state 与 slot,依次断言:冷查询恰好算一次、紧接的热查询不重算、
    写入之后**先直接**断言 fresh/stale 且写入本身不触发任何重算、下一次查询按相关性 +1 或
    +0、再次查询不变；同一源再推进一次并重复检查，证明槽保存的是连续版本快照而不是
    「零/非零」脏标志。
    q/v 分离由两格夹死:#4/#9 `{q,FP}` 写 v 后必须保持新鲜,#8/#12 `{q,v,FP}` 写 v 后必须
    失效——共用单一版本的实现会在前者上错误重算。
  - 证明范围(如实收窄)：本 Goal 证明槽机制能表达这 8 种依赖集合,并能抓住声明的漏项与多项;
    **不能**证明未来真实计算器没有读取未声明的输入——类型系统看不进函数体内。那由 G27 的
    真实 fresh/stale 矩阵与冷热上下文值对照承担；重算次数仍由 G25 的通用求值器测试承担。

  - 只提供 `AddRevoluteJoint`、`AddPrismaticJoint`、`AddWeldJoint`，不建字符串式通用 Joint API、回退或兼容别名；quaternion-floating 只作为 `DeclareFreeBody` 的私有实现，其余六种关节当前无消费者，不进公共门面。
  - **Release 抓出的实质缺陷**：vendored 层用断言校验惯量与旋转,断言在 Release 被编译掉,
    门面于是静默接受了不可能的惯量与非旋转矩阵。G21 的第一方校验器已提取为
    `multibody_physical_parameter_validation`，由状态存储与门面共用——一份物理实现,
    不是两份可能分歧的。
  - 判别力：7 项注入全部被抓——成环、模型身份、自由/关节冲突、自由体不加关节、第一方惯量
    校验去掉、第一方旋转校验去掉、自连接。其中后两项最初**因错误的原因通过**(拦下它们的
    分别是越界检查与成环检查),已把测试改成只能被目标检查拦下。
  - 复核收口：公共 `FrameHandle` 现与 landed tree 的真实 frame 一一映射，关节直接消费该 frame，不再复制 pose 生成隐藏的 joint frame；固定 frame 的完整 pose 在 Debug/Release 共用同一第一方校验；极大有限轴先缩放再归一化，不因直接求范数溢出而污染模型。句柄只允许 `MultibodyModel` 的私有表示助手构造，公共命名空间不留下可由消费者补全的友元桥。自由关系的内部 quaternion joint 不进入公共 joint 名称、句柄或计数面。
  - G29 不提前占用 G30 的稳定查询范围：构建期只返回后续加入操作必需的语义句柄；元素计数、名称查询、World 是否计入范围及自由关系的最终查询形态由 G30 在模型冻结后一次定义。

- [ ] **G30 — 实现最终化与稳定索引查询**
  - 产物：同一个 `MultibodyModel` 上只允许一次的最终化、不可变最终拓扑、模型工厂创建的
    `MultibodyEvaluationContext`，以及刚体、坐标系、关节和广义位置/速度区段的稳定语义
    查询；不另造一套兼容模型或暴露内部 tree/state/layout。
  - 最终化状态机：先完成所有不会改写底层 tree 的第一方预检——每个非 World 刚体到 World
    必须恰有一条无向路径，不可达者逐名拒绝。预检通过后才为 G29 记录的显式自由关系统一
    注入私有 quaternion 关节并进入底层 `Finalize()`；一旦该阶段抛出，模型进入响亮的终止
    失败态，不在可能半最终化的 tree 上重试。成功后结构、重力向量与模型自有力元常量冻结，
    任何 Add/建模期 setter/第二次 Finalize 都在入口拒绝。
  - 上下文门：最终化前不能创建上下文；公共上下文不可复制移动，只能由其模型工厂以默认
    参数与默认状态完整安装后发布，且模型必须比上下文长寿。不得重新开放原始布局、零填充
    状态或缓存工作区入口。
  - 查询范围：刚体查询不含 World；frame 查询只含 World、body frame 与门面创建的 fixed
    frame；joint 查询只含公共 joint，不含显式自由关系的私有关节或其他 ephemeral 元素。
    现有句柄在模型生命周期内稳定，支持按名称查询和确定顺序枚举；不为不存在的删除/重建
    语义增加代际句柄。
  - 坐标区段：提供具名的 `GeneralizedPositionRange` 与 `GeneralizedVelocityRange`
    （起点、长度），公共 joint 按 `JointHandle` 查询，显式自由体按 `RigidBodyHandle` 查询。
    两类区段互不重叠且并集精确覆盖最终 q/v，焊接区段长度为零；不暴露 `MobodIndex`、
    `LinkOrdinal`、`q_start`、`v_start` 或内部 quaternion joint。
  - 正确性门：串联、分支、焊接、自由体、混合关节与 World 为 child 的反向关系复现 G14；
    断连模型点名失败；最终化前创建上下文、最终化后改结构/重力、跨模型句柄均点名失败；
    公共计数与区段证明底层没有为未声明关系自动补自由度。显式自由语义不读取上游
    `is_floating_base_body()`，该标志只描述底层自动生成的 ephemeral 基体。

## 依赖与并行规则

默认关键路径：

```text
G01 → G02 → G03 → G04 → G05 → G06 → G07 → G08
    → G09 → ... → G45 → G46/G47 → G48 → G49 → G50
```

允许的有限并行：

- G08 完成参考语义后，可与 G09–G11 的源码边界工作并行。
- G18 可与 G15–G17 的编译工作并行，但 G19 必须等两边完成。
- G37–G38 可并行准备，G39 汇合。
- G46 与 G47 可并行，二者都完成后才能开始 G48。

除上述情况外，Goal 模式按编号顺序执行，避免后续 Goal 反向塑造前置接口。
