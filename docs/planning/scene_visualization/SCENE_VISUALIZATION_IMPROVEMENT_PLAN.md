# 三维场景显示综合完善计划

本文承接已落地的公共场景采样、场景记录与 IRW Web 查看器，安排下一轮代码整理、GZ18 接入和后续显示扩展。现状按 2026-09-28 的仓库代码核对；下文明确区分已有能力与待实现内容。

目标是让不同车型、线路和工况共用同一个查看器，而不是为 GZ18 复制一套 IRW 前端。先整理数据关联与代码接口，再补车型示意素材，最后按实际需要增加研究量展示和本机实时预览。

本文件是实施计划，不代表各阶段已经完成，也不自动授权同时启动全部阶段。

## 1. 已定边界

- 原生 C++ 负责动力学、运动学和物理观测；浏览器负责呈现已有结果，不重做动力学、线路定义或轮轨接触求解。
- 三维观察的公共数据与采样留在 `libs/scene_observation`，记录读写留在 `libs/scene_record`。它们不依赖 React、Three.js、网页布局或 UDP。
- 自包含查看器、离线记录、本机实时接入和第三方 UDP 是不同的消费方式。共享数据含义，不代表共享传输协议；不建立 UDP 转 WebSocket 的必经链路。
- 不涉及 RCZ，不修改第三方 UE 显示路线，不以仓外项目作为本轮验收前提。
- 实时渲染不得为了帧率改变积分步长、停靠点、控制时钟或接受态提交时机。离线回放的刷新率与播放速度由查看器自行决定。
- 不新增或复用 STL 等外部网格资产。继续使用盒体、圆柱、球体和参数化轮截面；示意外观不冒充制造几何或真实接触型面。
- 视觉定义保留在车辆库的独立 JSON 中，不把材质、颜色、相机偏好塞入机械配置，也不让 C++ 为美术字段增加公共接口。
- 允许清晰的破坏性接口更新，同次修改受影响的仓内生产者、消费者和测试；不留别名、历史格式读取器、迁移器或行为兼容开关。
- 遵守 NO SHA：不以提交号、内容摘要或哈希识别配置、锁定依赖、绑定安装件或判断记录兼容性。不增加格式版本号分支。
- 不建立插件体系、事件总线、通用组件注册框架或无人消费的占位接口；不新增 ADR、成套审查流水线或文献表。

命名、可信记录解析与接口更新同时遵循[第一方工程约束](../../engineering/FIRST_PARTY_ENGINEERING_RULES.md)。

上一轮已修复的内容继续保留：IRW 俯视航向与原始摇头标量分开、未知接触不当作单点接触、记录加载失败有提示、长记录摘要不使用大数组展开、无视觉定义时显示坐标轴与示意车轮、`hide` 优先于显示模式。它们不是下一轮要重新建设的功能。

当前仍有以下隐含绑定：

1. `readout_model.ts` 按 `carbody`、`axlebridge`、`wheelset`、`frame`、`bogie` 前缀猜角色，并按首帧纵向距离小于 0.3 m 猜轴位和载体。
2. `scene_builder.ts` 等位置仍直接使用 `carbody` 名称或 IRW 显示用语。
3. 载体俯视航向取刚体自身的 `+x`；这对当前 IRW 非自转轴桥可用，对包含滚动自转的 GZ18 刚性轮对不可直接使用。
4. `camera_rig.ts` 的目标偏移与取景宽度含 IRW 尺寸，不会随车辆长度与部件布局自然改变。
5. `SceneViewport.tsx` 按部件到构架的距离分配标注障碍，`VehicleCards.tsx` 按最近构架纵向位置分配俯视图面板。即使读数模型改成显式绑定，这两处也不能继续独立猜分组。

GZ18 实际名称是 `front_bogie_frame`、`front_leading_wheelset` 等。只增加几个前缀条件，既不能解决关联来源，也不能解决轮对自转和相机构图问题。

## 3. 分层与代码归属

```text
ORVD 模型、接受态或成功返回的采样状态
                  │
                  ▼
libs/scene_observation：拓扑、位姿、物理显示数据及其单位/坐标语义
          ├── libs/scene_record：完整离线记录
          ├── ORVD 应用中的本机实时适配（后续）
          └── tools/state_stream：独立第三方输出

离线记录／后续本机实时输入
                  │
                  ▼
查看器：输入解析 → 一次性显示绑定 → 场景、读数、相机、标注
                  ▲
车辆库独立视觉定义：示意零件、双语名称、显示角色与排列
```

公共能力不等于把所有前端代码也搬进 `libs/`。渲染对象、相机、布局和卡片仍属于 `apps/scene_viewer_web`；可由不同车型复用的前端模块在该应用内部共享。没有第二个前端消费者时，不拆独立 npm 包。

| 位置 | 职责与改动边界 |
|---|---|
| `libs/scene_observation` | 从真实模型与接触定义提取关系，不读取视觉 JSON，不猜车型 |
| `libs/scene_record` | 保存上述关系、帧值和状态；视觉 JSON 继续原样携带 |
| `vehicle_library/<vehicle>/visualization/` | 示意尺寸、刚体显示角色、双语名称和显示顺序，不复制物理参数 |
| `apps/scene_viewer_web/src/record` | 读取当前记录字段，建立数值与坐标语义，不承担车型推断 |
| 查看器新增显示绑定模块 | 将显式名称一次解析为刚体槽位、标量索引、轮位和显示区域 |
| `src/scene`、`src/ui`、`src/viewer` | 消费绑定，复用几何、材质、相机、卡片与交互 |
| `tools/dynamics_qualification` | 把既有样本交给公共采样和记录层，补齐 GZ18 开关，不另写导出器 |

共同数据约定继续保持：

- ORVD 惯性系 `+z` 向下；当地线路系才有随线路变化的纵向、横向与竖向轴。不能把固定惯性系的 `+x` 说成沿整条曲线的增里程方向。
- 刚体四元数为体系到惯性系的旋转，记录顺序是 `w,x,y,z`。到 Three.js 的统一显示变换只在根节点做一次，不在各卡片和几何函数中另换分量。
- 站位是线路平面投影里程，不是三维弧长。线路架来自记录，不在前端重新解算曲率、超高或竖向剖面。
- 记录物理量保持原单位，毫米、毫弧度、千牛等只在显示边界转换；原始摇头定义、标量有效状态和样本阶段不能丢失。
- 样本时间与索引继续使用当前记录的精确表示边界。位姿插值只是显示估计，不冒充新的 ORVD 求解状态或接触结果。

## 4. 第一批：关联、命名与共用接口

### 4.1 车轮到载体的关联由公共拓扑提供

在 `SceneWheelPlacement` 增加 `carrier_body_name`，由 `DeriveWheelPlacement` 从接触计划中已有的 `carrier.body_name` 赋值，不能取 `interface.carrier_name` 或 `carrier.carrier_name`：

- IRW：车轮刚体是独立轮，载体刚体是轴桥。
- GZ18：左右车轮挂在同一个刚性轮对上，车轮刚体与载体刚体相同。

该字段表达关系，不是新的车型枚举。不要仅凭两个名称相等就推断全部关节能力；未折返角是否可用仍由实际采样能力决定。

改动必须贯通以下位置，而不只是 JSON 写入器：

1. `scene_topology.h/.cc` 的值类型与拓扑构造。
2. 场景记录写入、C++ 读取、TypeScript 解析。
3. 拓扑测试、记录往返测试、前端测试夹具及所有相关初始化点。
4. 当前记录说明；本地演示记录需用完整导出路径重新生成，不入仓，不增加旧记录回退。并行工具任务未交接时，不借本批重新配置或构建该任务使用的构建树。

查看器按载体关系归组，再按 `side` 找左右轮，不再用 0.3 m 判定它们是否属于同一轴位。位置只用于显示尺寸与排版，不承担拓扑身份，也不覆盖明定的显示次序。

当前两车都是每个载体对应一组左右轮。若后续模型不满足这个关系，应先扩展真实拓扑表达，而不是在 UI 中静默取第一对轮。

载体轨道坐标标量的命名约定是 `<载体刚体名>.track_station_meters`、`.lateral_meters`、`.yaw_radians`；接口标量使用 `<接口名>` 前缀。这是车辆导出者与查看器之间的对接约定，不限制通用 `scene_record` 保存其他有完整定义的标量。

当前共同运行器在两处依赖 carrier 名与刚体名相同：`MakeSceneScalarDefinitions` 用 `carrier_name` 生成前缀，观测循环之前的 `carrier_bodies` 也用它查找刚体。两处都应显式取 `carrier_definition(i).body_name`。IRW、GZ18 当前恰好满足两名相同，因此这是解除闭合场景假设，不是修正两车已算出的结果。

这两处位于并行工作区，按第 10.3 节暂缓生产端落位。首批可完成公共字段与消费侧契约，但不能在生产端尚未修正时宣称载体标识与刚体名不同的完整导出链路已经可用。

### 4.2 视觉定义只补显示绑定

在既有视觉定义中加入当前卡片、相机和标注实际需要的绑定：

- 车体对应的刚体与双语名称。
- 构架列表、显示次序、对应刚体与双语名称。
- 载体的显示名称及“轴桥／轮对”等术语；需要分属某个转向架面板时，显式给出显示分组。

当前不增加朝向字段。位姿与零件局部坐标保持原义，端序由显示列表给出；未来只有出现具体消费者需求时才讨论额外方向数据。

不在视觉定义中再次填写车轮半径、侧别、载体归属、质量、惯量或接触常量。几何挂接继续使用已有 `parts.body_name`；物理关联来自公共拓扑。

构架列表显式给定端序，避免通过英文前缀或刚体 `+x` 临时拼出“一位端”。通用模块使用“载体”“轮对位”等中性概念，IRW 界面可以由数据写“轴桥”，GZ18 可以写“轮对”。

没有视觉定义是允许的显示能力缺失：保留坐标轴与示意轮模式。载体分组、左右轮、已记录的载体读数、轮重和接触状态仍由拓扑与标量提供，不能随整组卡片关闭；名称可直接显示原始刚体／接口标识，不猜端序。缺少的只是车体与构架角色、其专属卡片行及转向架镜头等显示能力。

需要区分三种情况：绑定引用不存在的刚体，在一次性解析时报错；刚体存在但没有所需标量，保留几何并让相应读数显示“未记录”；标量存在但当帧未就绪或占位，继续显示记录携带的状态。当前导出只覆盖载体与资格配方的三个代表刚体，不因显示绑定增加而自动生成其他刚体的轨道坐标观测。

### 4.3 一次解析，多个消费者共用

建议增加 `vehicle_display_bindings.ts`，用普通值类型和一个解析函数完成绑定，不建立注册器或继承树。内部继续使用 `carrierBodyName`、`CarrierReadoutBinding` 等 carrier 词汇，“轮对位”属于界面文案。

绑定结果包含现有消费者需要的刚体槽位、载体与轮位关系、双语名称及显示分组；读数模型再据此解析所需标量引用。卡片、相机锚点、部件显隐和标注障碍使用同一份关系，不分别扫描名称。

保留现有模块的职责：

- `readout_model` 负责记录读数、有效状态和单位显示，不再发现车型拓扑。
- `scene_builder` 负责建立渲染对象，不再判断某个刚体是不是 IRW 车体。
- 相机与标注只使用明确的显示对象集合，不把同一名字规则复制到各模块。
- `App` 编排加载、播放与页面状态，不内嵌物理关联推断。
- 俯视图的构架分组与视口的标注障碍分组都来自同一显示绑定。首帧位置可决定局部尺寸与排版，不决定归属或覆盖显式端序。

先让 IRW 使用这条路径，再用 GZ18 或其真实命名的短夹具验证复用。不得留下“显式绑定失败后按前缀猜”的第二条实现。

### 4.4 命名按语义整理，不按字符数加长

跨模块名称应说明对象、量纲和必要坐标系，并尽量与记录字段使用同一词汇。记录下划线字段到 TypeScript 驼峰字段的转换不应丢掉语义。

| 当前例子 | 整理方向 |
|---|---|
| `Loaded` | `LoadedSceneReplay`，明确装载对象 |
| `Bi` | 组件改为 `BilingualLabel`；双语数据复用已有 `BilingualName`，两者职责不同 |
| `ReadoutModel` | `VehicleReadoutModel`，明确是车辆读数而非任意页面模型 |
| `WheelRef.force` | `verticalSupportForceScalar`，不能与法向力混称 |
| `WheelRef.normal` | `normalForceScalar` |
| `AxleRef.bridge` | 以 `CarrierReadoutBinding` 明确承载对象，字段使用 `carrierBodyName` 等已有词汇 |
| `TrackBodyRef.offset` | `initialLongitudinalOffsetInCarbodyFrameMeters`；无车体参考时不可用，不能仍填世界系偏移 |
| `frameA`、`frameB` | 表示帧表行号时用 `firstFrameIndex`、`secondFrameIndex` |
| `frameAt` | 表示坐标架查询时用 `trackFrameAtStation` 等明确动作名 |
| `leftRailV/W` | 按实际含义写出左轨横向／深度偏移、参考系及米制单位 |
| `gauge` | 当前量若是两条轨面基准线的间距，使用 `medianRailDatumSpacingMeters`，不冒充物理轨距 |

表中名称是按当前职责给出的方向；实际落位时同一个语义只保留一个名称，文件名与导出类型一起检查。

另统一三个多义词：

- 帧表行号用 `frameIndex`；`sampleIndex` 专指记录身份列中的样本序号，它由运行程序提供，可与行号不同，也不是积分器内部步号；参考系用 `trackFrame`、`bodyFrame` 等。
- 帧表列偏移用 `columnOffset`；例如样本身份列的位置与该列的值不能都叫 `sampleIndex`，整理时区分 `sampleIndexColumnOffset` 与 `sampleIndex`。部件位置偏移必须标出方向、参考系和单位。
- 里程值用 `stationMeters`，站位循环下标用 `stationIndex`。

`Card`、`SceneRecord`、`TrackModel`、`PlaybackController` 等已有清楚职责的名称不为长度修改。紧邻公式的短数学变量和简单循环下标可以保留。共用算法不加 `Irw`、`Gz18` 或工况前缀；车型专属资产仍可使用真实车型名称。

### 4.5 记录说明随接口落位

第一批新增简短的 `libs/scene_record/README.md`，集中说明目录组成、帧布局、坐标与单位、`frameIndex`／`sampleIndex` 区别、整数身份范围、缺测状态以及完整记录的关闭条件。已有头文件已承载这些契约，README 链接接口，不复制出另一套独立维护的规格或校验脚本。

车辆标量命名约定单独注明其适用范围与生产端落位状态。`scene_record` 本身仍只保存调用方提供的标量定义、数值和状态，不检查名称是否属于车辆读数集合。

## 5. 第二批：跨车型显示语义与几何收尾

### 5.1 轮对位俯视航向改用轮轴方向

记录的 `yaw_radians` 是已登记的体基分解标量，不是统一的俯视航向。继续原值显示，并保留其定义；不为二维示意图修改 C++ 的物理观测。

轮对位示意转角由已记录的车轮姿态与自转轴计算：

1. 将 `spin_axis_in_wheel_body_frame` 用该轮记录姿态变到惯性系。
2. 投影到当地线路的纵横向平面，取靠近线路正横向的半圈分支。
3. 由此得到轮对位相对线路的俯视航向，向右轨转为正。

这条方向不随车轮绕自身轴的自转而变化，适用于 IRW 与 GZ18。它仅决定示意图的平面方向，不替代原始摇头、侧滚、点头或冲角。

车体和构架继续使用其明确的纵向轴；不要把轮对的轴向算法无差别套到所有刚体。投影退化或缺少必要记录时不伪造角度，显示不可用。

测试夹具保持真实的姿态关系：IRW 相对自转只改变独立轮角度，轴桥不随之自转；施加整体摇头或侧滚时，载体与轮体姿态同步变化；GZ18 两侧轮位始终共享轮对刚体姿态。覆盖零、四分之一周、半周自转及其与摇头、侧滚的组合，不能用只转轴桥却不更新轮体整体姿态的夹具证明通用性。

### 5.2 相机构图来自显示对象尺寸

保留现有跟随、沿线朝向和视角补间算法，改掉按 IRW 长度填写的 9.4 m 目标偏移及整车取景宽度。

- 根据绑定选出整车或所选转向架的零件、车轮集合，求显示范围；计算时排除线路、地面、坐标轴与文字标注。
- 首次装载时在合适的车辆局部坐标下求范围，避免车辆在曲线上旋转造成世界轴对齐包围盒尺寸跳变。
- 根据视角、视口纵横比与卡片实际占用区域拟合距离和目标点；允许少量有名称的留白比例，不再填写车型长度常量。
- 载入记录、切换预设和窗口尺寸变化时更新必要的取景范围，同时尊重用户手动环绕与缩放，不逐帧强制复位相机。
- 相机方向、视场角、补间时长属于美术偏好，可留在查看器；不要把每个具体相机坐标塞入车辆 JSON。
- 缺少某个构架绑定时，不把“转向架镜头”静默指向车体；该选项应明确不可用。

### 5.3 只修已确认的线路边界

`track_builder.ts` 的道床和路基沿线网格用向下取整决定站位数量，非整米长度会漏掉尾段。钢轨本身已经使用完整记录站位，不应把本问题扩大成全部线路重写。

- 道床、路基采样必须包含起点与终点，不重复生成退化尾面。
- 验证非整步长、短于一个步长及恰好整步长的区间。
- `track_model.ts` 当前先在平台内部点上判断 4 m 长度，再向边界扩展，会漏识别部分短圆曲线。先确定可确认的平台边界，再判断跨度。
- 保留已经实现的不同半径平台分离；补短平台、短过渡及记录两端的用例，不能通过吞掉真实过渡段让分类看起来连续。

曲线类型仍是由采样表推导的显示说明，不是线路定义的第二权威来源。不能从有限采样中保证恢复所有线形边界；没有足够证据时保留这种分辨率限制。

### 5.4 UI 与资源小项随相关模块收口

此前记录的开发模式重复释放、相机贴近时标注障碍框、布局安全区与 CSS 重复、`placement_note` 措辞，先确认当前是否仍存在，再在相应模块中局部修正。

资源由创建方统一释放；标注与相机使用同一份布局区域；遮挡裁决不改变物理数据。这些小项不成为新框架、整页重写或 GZ18 接入的扩张理由。

## 6. 第三批：GZ18 最小接入，再做美术

### 6.1 接通现有共同导出路径

当前共同资格运行器已经支持 `publish_scene_record`，但 GZ18 入口尚未透传。沿以下位置补齐：

- `run_gz18_qualification.cc` 的可选导出参数。
- `Gz18QualificationRunConfiguration` 及其到共同运行配置的适配。
- `vehicle_library/gz18/visualization/visual_definition.json`。

继续使用共同的 `SceneRecordExport`、公共拓扑与样本循环，不复制一份 GZ18 记录写入器。现有导出路径需要视觉文件，第一份 GZ18 文件先提供必要绑定和简单示意体，随后再细化外观。

最小闭环是一段短直线记录：正确加载车体、两台构架、轮对及八个轮位；左右轮使用同一轮对刚体的不同放置基准；卡片、镜头、标注均沿用共用代码。随后用一段短曲线记录核对坐标和跟随，不安排长窗资格或整车性能比较。

GZ18 当前资格配方要求显式指定不平顺资产，短直线记录也不例外；不增加无不平顺特例，不改变冻结资产。记录中的线路采样表仍表示设计线形，不由此宣称已显示不平顺钢轨。其代表刚体为车体与前后构架，两台构架已有相应的轨道坐标标量。

本批开始前完成第 4.1 节的两处生产端修正，并核对前序并行工作已经提交、交接；不得只补导出开关而遗漏载体关联的实际使用点。

### 6.2 不把刚性轮对自转能力说满

当前 `WheelSpinAngleSampler` 依赖独立回转副广义位置。GZ18 的刚性轮对自转包含在轮对姿态中，没有对应的独立关节展开角，因此现有记录不提供该列。

- 已有姿态仍是权威结果，不按车速除半径额外叠加轮自转。
- 细采样下可沿用姿态插值，但需依据实际角速度、样本间隔和中间姿态检查分支；不能只按名义速度承诺正确。
- 当前无展开角诊断使用的四分之一周警告阈值，不等于最短路径的半周歧义边界。GZ18 的 0.42 m 是名义半径，不是轮径。
- 首次接入不为粗采样新造角度积分器。确需粗记录准确回放时，再单列“刚性轮对展开自转信息”的采样与验证工作，不能把不可辨认的多圈数猜出来。

### 6.3 美术沿用同一套要素

GZ18 先具备可核对的示意外观，再参考 IRW 已成型的暖浅背景、半透明车体、橙色运动件、双侧卡片和引线标注做细化。

新增内容以车辆视觉 JSON 为主。材质、基础几何、轮截面、标签排布、时间轴和卡片共用；不复制 `Gz18CameraRig`、`Gz18Playback`、`Gz18TrackBuilder` 或整套车型页面。

两车可以有不同示意尺寸和双语名称，但不能各定义一套力、坐标、时间和接触状态语义。默认仍按原比例显示，若增加变形或不平顺放大，必须显式标明倍率和图层。

## 7. 后续扩展：物理显示量先有来源，再有图层

这些不是第一批整理的前置条件。前述共用链路稳定后，按需要分别实施。

### 7.1 逐斑接触点与力箭头

当前轮级斑数与力标量只能支持颜色和读数，不能据此恢复接触点位置。新增叠加应复用 ORVD 真实接触观测，不在浏览器重算。

- 公共场景层负责将 carrier Track-T 中的接触点与力转到惯性系，分别正确处理点的平移和向量的旋转。
- 换算使用同次求值对应的 carrier 站位。当前观测中的侧别轨型参考站位不是 carrier 原点站位，不能混用。
- 若现有公开数据不足以可靠取得该站位，在观测结构增加所需的窄字段；不要提前追加一组尚无消费者的查询。
- 在独立观察上下文和自有工作区求值，携带该样本所需的保持量和投影历史，不污染积分器接受态、试算态或其缓存。
- 记录保存逐样本、逐接口的变长接触列表及其时间身份。某次求值的斑序号不是跨时间身份，不把“第一斑”自动连成轨迹，也不跨接触生灭插值箭头。
- 未就绪、有效无接触、单斑与多斑分别呈现；竖向支承力、法向力和接触坐标系切向力保持不同名称。
- 当前观测没有完整接触斑几何，不能凭力值画出声称真实的接触椭圆。精确的点／力换算由导出端完成，不用静态稀疏线路表插值冒充同次求值的坐标变换。

导出频率由仿真观测需求和成本选择，与浏览器刷新率无关。当前场景记录不包含完整连续状态及投影历史，因此不承诺离线凭位姿补算接触。

### 7.2 实际不平顺场显示

从所选 ORVD 运行使用的实际不平顺场按里程采样，不从 PSD 名称或 seed 在浏览器重新生成。

保留设计线形与实际位移图层的区别。公共数据说明参考系、通道、单位、placement 与有效范围；查看器仅做插值和显示。加入横向／竖向位移不等于复现接触求解器完整轨面放置，更不等于已有真实钢轨截面。

放大显示只改变图层，必须标明倍率；不能用放大后的钢轨与未放大的车轮位置推断接触误差。当前 AAR/ERRI 生成、冻结资产和车辆工况均不因显示而改动。

## 8. 后续本机实时：不让显示决定推进

区分三种时间：仿真时间、样本时间、浏览器墙钟刷新时间。相机、播放和 WebSocket 发送频率不能反向决定前两者。

当前 `AdvanceToWithDenseStateSamples` 在一次推进成功后返回完整样本矩阵，中间样本不是新的数值停靠点。资格运行器先完成整窗推进，再在观察上下文中处理样本并写记录。因此现有路径不是边积分边显示。

有既定控制或应用事件边界的运行，后续可采用：

1. 推进成功返回，在已有边界读取已提交状态或已返回样本。
2. 仿真线程将完整场景帧交给有界的最新帧槽，不把可变 Context 指针交给发送线程。
3. 应用侧发送线程通过本机连接推送；慢客户端允许丢显示帧，不能产生无界队列或阻塞积分。
4. 查看器的实时输入与离线输入交给同一套场景、读数和绘制函数；只在真正实现实时接入时增加必要的输入适配，不现在预建空接口。

一次调用覆盖整窗的运行仍结束后回放。要在这类推进中途观察，必须另行明确公共输出时机与失败事务，不能为了 30/60 Hz 显示把推进调用切成小段，也不把读取增长中的未关闭记录当作当前支持能力。

“不干扰积分”指不改变数值推进与状态语义，不代表采样、复制和传输没有墙钟成本。验证时分别核对状态／积分工作量不受显示开关影响，以及慢客户端无反压；观察成本独立报告，不承诺零耗时。

播放、视角、显隐和定位始终只影响显示。前端物理参数调节、任意外力拖拽、远程控制接口不在此计划内。

### 12.3 显示绑定的最小输入与解析结果

在现有视觉 JSON 中增加 `display_bindings`。首轮采用以下形状，不再增加方向字段或车型枚举：

| 字段 | 内容与消费者 |
|---|---|
| `carbody` | `{body_name, display_name: {en, zh}}`，或显式 `null`；用于车体读数、显隐与相机锚点 |
| `bogies` | 有序数组；每项为 `{body_name, display_name, member_body_names}`，用于构架读数、镜头顺序、俯视图分区与标注障碍 |
| `carriers` | 有序数组；每项为 `{carrier_body_name, display_name}`，用于载体行、名称与显示次序 |

有视觉定义时使用这套当前结构；无视觉定义仍是合法的拓扑示意模式，不借此保留旧视觉结构读取路径。构架数组可以为空，车体可以明确不指定。

`member_body_names` 只表达显示分组，不建立动力学父子关系。构架自身隐含属于其组；轴桥／轮对、导向杆等需要纳入该显示区域的刚体由 JSON 明列。车轮通过公共拓扑的 `carrier_body_name` 继承分组，不在视觉 JSON 重抄左右轮清单。重复或冲突的组归属在一次性解析时指出，不用最近距离裁决。

成员集合按刚体槽位去重，左右轮 placement 则分别保留。GZ18 两侧车轮共用一个轮对刚体是正常关系，不是重复归属错误。

载体名称与次序覆盖当前记录的载体集合；物理侧别和轮体仍从拓扑取得。没有视觉定义时，按拓扑首次出现顺序列出全部载体，使用原始刚体／接口名，不能暗示该顺序是前后端序。

现有 `parts[].label` 和 `wheel_visual.labels` 继续用于三维引线，它们只标注选定零件，不能拿来充当完整载体列表。共用卡片标题使用“Carriers · 载体”，行内保留数据提供的“轴桥／轮对”具体名称。

新增 `src/scene/vehicle_display_bindings.ts`，提供普通函数 `resolveVehicleDisplayBindings(record, visualDefinition)`。返回车体槽位、有序构架及成员槽位、载体及左右轮 placement 索引、显示名称和组关系；不保存渲染对象，不建立注册器。标量引用在读数模型构造时按这份绑定解析一次，不在每帧重新查找名称。

名称引用的检查集中在该边界：被引用刚体不存在是输入关系错误；标量未导出是能力缺失。解析器只负责字段读取，不在每层重复检查整份关系。缺少横移／摇头标量时，表格显示“未记录”；二维示意也不能把缺测值当零位移画成测量结果，不为补图临时重算物理观测。

没有车体绑定时，车体系纵向偏移本身不可用，不沿用当前世界原点／世界 `x` 方向代替。依赖该参考的二维布局可以明确不显示，载体、轮重和接触表格仍保留；这不要求在首轮新增另一套几何投影。

### 12.4 装载记录后的调用顺序

```text
loadRecord → 读取帧表与当前场景字段
           → 解析一次视觉定义（允许没有视觉定义）
           → resolveVehicleDisplayBindings
           ├─ buildScene：零件挂接、车体显示角色、线路和轮体
           ├─ buildVehicleReadoutModel：绑定标量、状态与显示尺度
           └─ SceneViewport／卡片：共用相机锚点、成员分组和名称
```

`App` 的装载结果命名为 `LoadedSceneReplay`。视觉解析从当前 `buildScene` 内移到装载边界；场景构造和读数模型使用同一份解析结果，不互相依赖去获取车型身份。求线路显示模型的现有步骤可留在场景构造中，不为此新增装载管理器。

必须同时迁移的消费者：

- `readout_model.ts`：删除前缀筛选、0.3 m 归组、邻近载体匹配和由位置覆盖显示次序的逻辑。
- `scene_builder.ts`：车体分组改用绑定，不再比较字符串 `carbody`。
- `App.tsx`、`SceneViewport.tsx`：相机锚点与标注障碍使用绑定成员，不再按最近构架分配部件。
- `VehicleCards.tsx`：载体行、俯视图构架归组与名称使用绑定；距离仅用于绘制尺寸与位置。
- `ControlCards.tsx`：转向架镜头标题和锚点对应同一个显式构架，缺少角色时禁用该选项。
- `camera_rig.ts` 与视口初始化：移除角色猜测后，无视觉定义时仍须有基本可用的场景视角。以记录刚体位置范围的中心设置普通观察目标并使用默认观察距离，不把某个刚体假定为车体；不在首轮实现第二批的尺寸自适应取景。按钮、快捷键及 URL 中的角色镜头请求统一按实际绑定判定可用性。
- `TrackCard.tsx`、`PlaybackCard.tsx`、`subtitle.ts`：没有车体角色时保留不可用语义，不另选一个刚体顶替。

命名修改沿受影响接口一次迁移：`LoadedSceneReplay`、`VehicleReadoutModel`、`CarrierReadoutBinding`、`BilingualLabel`，以及帧行号／样本身份／列偏移。若重命名文件，同次更新全部 import；不保留旧导出别名。`playback.ts`、`apply_frame.ts` 等若受帧参数改名影响，只改名称和调用方，不借机改算法。

### 12.5 用短用例检查关系，而不是再跑长仿真

首轮补齐以下反例，避免当前 IRW 名称与布置恰好掩盖问题：

1. carrier 逻辑名与载体刚体名不同，公共输出必须取 `body_name`。
2. 刚性轮对左右 placement 共用同一轮体和载体；IRW 则轮体与载体不同，两种关系都成立。当前单纯使用单位体基的夹具不能冒充前一种关系。
3. 两个载体纵向位置很近仍分开，同一载体的轮位不因位置距离改变而拆组；颠倒 wheel 数组顺序仍按 `side` 归属。
4. 所有刚体改成不带约定前缀的名称，仍按显式角色工作；显式构架顺序与几何排序相反时不被改回去。
5. 无视觉定义仍保留基本三维视角、载体、轮重、接触状态与事件；无某个标量只影响相应读数，不丢掉该载体或整车。不可用角色镜头不能经快捷键或深链绕过按钮限制。
6. 未知刚体引用与标量缺失分别处理；不能用同一 `null` 掩盖错误引用。
7. 帧表行号为 `[0,1,2]`，样本身份为 `[42,105,901]`：定位、插值帧区间和接触事件使用行号，界面身份显示取记录值；同时保留身份 `-1` 的既有含义。

现有 C++ 场景测试目标足以承接首轮字段用例，不修改顶层测试 CMake。前端沿用 `node:test`；必要时增加小型记录解析／绑定测试文件并加入现有 `package.json` 列表，不引入测试框架或大型数值记录。

实施后的直接验证范围是三个既有场景 C++ 目标，以及前端测试、类型检查和打包。真实 IRW 拓扑测试只需装配，不推进时间。浏览器用程序化小记录检查接口迁移；已有演示记录缺少新字段时明确拒绝，待工具任务交接后再重新导出，不能手工补字段后当作生产闭环证据。

安装消费只做针对性核对，不运行全量安装门。现有 `scene_record_installation_smoke` 的无轮样例不覆盖新载体关系，且目前总安装脚本没有显式运行该目标；不能把“已注册／已编译”报告成新字段运行验收。若本批实际做安装冒烟，应单独明确所运行的目标，不顺带扩展安装框架。

### 12.6 实际开工顺序与首轮收口

1. 先贯通公共字段、C++／TS 读写和直接夹具；数据字段来源明确后再动 UI。
2. 补 IRW 的显示绑定与解析函数，先用无前缀、同体轮对、无视觉定义的短夹具检查关系。
3. 调整装载顺序，逐处切换读数、场景、视口和卡片消费者，同时完成名称迁移。
4. 补简短记录 README 和现有查看器说明，执行本节的直接验证与差异自检。
5. 单独列出尚未做的两处运行器修正、真实记录重导、第二批算法与 GZ18 导出，不把它们算作已完成能力。

在并行工作未交接时，首轮仍可完成公共字段、消费侧和小夹具，但不重配共用构建树、不启动资格运行器。生产端补齐后，才能用新导出的记录关闭完整链路验收。这样隔离的是文件与执行资源，不是保留两套接口或建立历史兼容模式。
