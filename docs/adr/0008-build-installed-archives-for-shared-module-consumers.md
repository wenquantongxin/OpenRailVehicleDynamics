# ADR-0008：安装归档统一支持进程内共享模块消费者

- 状态：**Accepted**
- 决策日期：2026-08-18
- 相关：ADR-0001、ADR-0002、ADR-0007

## 背景

ORVD 的公共 CMake 包最初主要由可执行程序消费，第一方安装目标是静态归档。轨道控制算法仓库需要
通过 pybind11 在同一进程内链接这些归档；若只为该消费者维护第二套 PIC 构建和安装前缀，两套前缀
会分别解析 Eigen、fmt、SUNDIALS、编译器选项和资产，实际已出现“名义只差 PIC、依赖输入也不同”
的风险。把 ORVD 源码作为子目录编进消费者则绕过安装边界，并会让私有目标意外成为接口。

可选方案还包括把全部 ORVD 产品库改成共享库。当前没有独立共享库 ABI、部署或多进程复用需求，
为 Python 扩展改变所有安装目标的库型会扩大运行时依赖与分发范围。

## 决策

ORVD 在顶层无条件设置 `CMAKE_POSITION_INDEPENDENT_CODE=ON`。所有当前及以后加入安装导出集合的
第一方静态归档均由位置无关对象构建；普通 C++ 可执行程序和进程内共享模块消费同一个安装包。
消费者只通过 `find_package(OpenRailVehicleDynamics CONFIG REQUIRED)` 使用导出目标，不维护按
消费者区分的 PIC 前缀，也不把 ORVD 源码并入自己的构建树。

共享消费能力的承重验收是：安装导出集合中的归档能够实际链接进共享目标，并由真实消费者加载。
不得用全构建树的 `-fPIC/-fPIE` 计数代替该验收；`-fPIE` 可以属于不安装的可执行目标，不能证明
静态归档适合共享链接。

## 后果

- ORVD 只有一个安装身份，依赖解析、公共头、资产和库不会因消费者类型形成双轨。
- 位置无关代码可能带来少量代码生成或性能差异，但不改变车辆物理、数值容差或公共 C++ 语义；
  性能结论仍须在记录了构建修订的代表工况上测量。
- 已在运行的外部二进制不受源码选项变化影响；下次从源码构建会重新生成相应对象。修改顶层构建
  选项后必须先执行正常的 configure/build，再运行 CTest，不能把陈旧构建树的直接测试结果当作
  当前源码证据。
- 本决策不承诺通用共享库发行、稳定的二进制 ABI 或把第三方动态依赖打包进 Python wheel；这些
  需求出现时必须按真实部署边界另行裁决。
