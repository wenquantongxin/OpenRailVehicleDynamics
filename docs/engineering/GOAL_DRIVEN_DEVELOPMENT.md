# 按目标推进的开发方法

把工作拆成可验收的目标，每轮对照实际实现与证据收口。代码、接口与数值验收遵循[第一方工程约束](FIRST_PARTY_ENGINEERING_RULES.md)，本页只说明如何组织开发与复核。

## 目标卡

开始前写清以下内容，规模以一个可独立验收的逻辑产物为宜：

- **目标与产物**：解决什么问题，完成后出现什么可观察的行为或结果。
- **前置条件**：依赖哪些已有能力，以及它们是否已具备。
- **修改范围**：涉及哪些模块和接口，本轮不包含哪些相邻事项。
- **完成条件**：用什么检查判断完成，各项检查能够证明什么。

直接相关的测试与必要说明随产物一起完成。若目标仍包含多个互不依赖的产物，先拆开；若前置条件或范围发生实质变化，先修正目标卡。

## 一轮闭环

1. **核实事实**：阅读目标涉及的实现、接口和直接前置产物，明确当前行为与目标之间的差距。
2. **形成方案**：说明改动位置、关键选择及理由，列出尚待验证的假设，并将完成条件落实为具体检查。
3. **实施与验证**：完成聚焦改动，运行与影响范围相称的检查；失败时定位原因并修正，完成条件满足后再标记完成。
4. **独立复核**：实施改动落定后，由未参与实施的一方从代码、接口与实际证据重新判断实现是否满足目标，主动检查遗漏和反例，不以实施报告代替核验。
5. **修正与收尾**：处理复核发现的问题，补做受修正影响的验证，记录结果、证据范围和仍然存在的限制。

复核以实现和可检查的证据为依据。发现问题后回到当前目标修正；新的目标另行描述。

## 事实与证据

报告应区分直接核实的事实、由事实作出的推断，以及尚未核实的他人报告。事实指出对应实现或验证结果；推断写明前提；引用他人结论时保留其归属与验证范围。

选择检查前先问：如果这个结论是错的，会出现什么不同？围绕这个差异选择最短而有效的核验。数值和事务变更优先使用解析关系、物理不变量、边界行为或状态提交性质；结构计数不能独自证明算法正确。

反例应对应真实可达的失败路径或输入边界，结论的适用范围以实际检查为限。

复核按改动、证据可信度和未解决的疑点选择检查。已有检查通过后，仅在新增改动、失败或未解决问题需要时扩大或重复验证。

## 结论与记录

任务记录说明本轮目标、关键选择、验证结果和完成边界，帮助接续工作。稳定的架构理由进入架构决策，当前能力和使用限制进入模块说明，算法依据与局部约束进入相应文档或代码注释，可执行的行为保证进入测试。

长期说明围绕当前事实维护，任务记录保留实施过程；不要把已结束的步骤、临时观察或旧完成条件继续当作现行要求。
