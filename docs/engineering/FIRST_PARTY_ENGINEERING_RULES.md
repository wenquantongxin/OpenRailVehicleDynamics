# 第一方工程约束

本文件是 ORVD 第一方代码的长期约束，**自本文件存在起即刻生效**，不是待实现的路线。
它约束我们自己写的代码；vendored 上游源码按其自身来源与许可证处理，不受此处命名与
接口规则约束。

## 1. 语义命名

文件、类型、函数与变量的名称必须准确表达其领域含义。**宁可稍长，也不要含糊。**

**禁止**用版本或时间标签区分第一方实现、接口或格式：`v1`、`v2`、`classic`、`new`、
`old`、`legacy`、`final`、`improved`。这类区分在写下的当天就开始过时，并且强迫读者去猜
"另一个是什么"。词语本身具有准确领域含义时不受此限，例如 `final_time`；上游的正式
版本号只可用于**来源追溯**，不得进入第一方的类型名、函数名或文件名。

**禁止**让低信息词单独充当名称的主要语义或泛化后缀：`p1`、`run`、`data`、`info`、
`manager`、`helper`、`util`、`process`、`handle`。准确的复合领域名称不受词面禁令；
判断标准仍是名称本身是否说明了对象或动作的具体职责。

模块和公共类型同样必须带领域语义。不得用 `core`、`common` 或裸 `Context` 占据第一方
公共名称；应写成 `multibody_runtime`、`SystemRuntimeContext` 等能说明作用域与所有权的
名称。vendored 实现里的内部术语不得泄漏为第一方公共 API；公开接口描述领域概念，不要求
调用方理解上游的内部数据结构。

发现违反的名称就**立即做小范围重构**，不记待办、不留注释解释。名称是接口的一部分，
延后重命名只会让调用方越来越多。

## 2. 变量名的长度边界

**默认使用完整变量名**：`generalized_positions`、`mass_matrix`、
`inverse_dynamics_generalized_forces`。

短数学符号（`q`、`v`、`M`、`tau`）**只允许**出现在含义由紧邻公式直接确定、且生命周期
极短的局部：一个表达式、一个紧凑的数学循环体。它们**不得**出现在公共接口、跨函数传递
的状态、成员变量或文件名中。

判据不是行数，而是：**读者是否需要一条补偿性注释才能确定这个名字指什么。** 需要，就说明
名字不合格——注释应当解释公式、物理假设与坐标约定，而不是翻译弱名称。

带完整坐标系语义、且下标方向遵循项目统一约定的标准记号（`R_WB`、`X_AB`）可以接受；
孤立的 `R`、`X`、`S` 不可以。循环下标 `i`、`j` 只限没有额外领域含义的紧邻循环，
否则写 `body_index`、`velocity_index`、`matrix_row`。

## 3. 不保留兼容层

**不保留**旧名称、旧格式、旧接口，或已知错误实现的兼容层。

接口改变时，**在同一次改动中同步修改全部调用方**。不新增别名、弃用包装、回退分支或
双轨实现。一个语义只允许一条执行路径。

不读取历史格式，不提供"旧行为开关"。被替换的实现在同一次改动中删除，由 Git 历史承担
追溯。

## 4. 可信内部输入采用宽松解析

由第一方自己生成、在自己进程之间传递的输入是**可信**的，按可信对待：

- 允许字段乱序、额外字段、当前未使用的字段；
- 重复的单例取最后一个值；
- 只检查**实际要使用的字段**能否解析、必要的维数是否正确，以及真正的语义前置条件。

不要为可信输入构建通用模式校验器，不要重复验证下游库已经验证的约束，不要假想不存在的
威胁模型。

但**缺少必需信息时必须明确失败**：不静默取默认值、不修补非法的物理量、不吞掉错误。
宽松指的是"不苛求形式"，不是"猜测意图"。

## 5. 只做必要的正确性检查

避免重复验证、冗余防御代码、提前泛化，以及无人消费的接口。

**非必要的裁剪、静默默认和错误吞咽会掩盖错误。** 一次把越界值裁剪回合法区间的"保护"，
可以把一个严重错误的输入变成一个看起来完美的结果——这类粉饰比崩溃危险得多。含糊即
失败，但"故意脆弱"指的是让错误尽早、响亮地暴露，**不是**放任未定义行为、内存不安全
或缺少诊断。

未支持的能力在**最早能够判定的边界**明确失败，例如编译、配置、模型最终化或请求解析，
而不是静默降级。不预先建造插件系统、类型擦除层或"将来可能需要"的抽象。

## 6. 热路径纪律

右端求值与缓存查询等热路径上：

- 不做非必要的堆分配与复制，优先复用预分配存储；
- 不做字符串查找、格式化与日志；
- 不引入无谓的间接层；虚接口只存在于外层，不扩散进内循环；
- 保持数据流直接。

数据进入热路径前，只在边界处检查实际使用字段、必要维数和真正的语义前置条件；不变量
建立后，内部热路径信任它们。

**但不得以性能为由牺牲已经要求的正确性。** 若两者确有冲突，先满足正确性，再把性能问题
作为独立事项处理。

## 7. 验收依据

不使用数值金标、输出快照、文件哈希或逐位一致作为验收依据。一个只能与自己历史输出比较
的测试，无法区分"仍然正确"与"一直错着"。

跨实现的物理数值验收采用工程容差：连续量以 `1e-3` 相对误差为主，近零量使用按单位声明
的绝对限，旋转使用 SO(3) 角度误差。直接验证某条代数定义的单元测试可以逐分量比较，并按
参与量级使用机器精度的小倍数；这类测试不得冒充跨实现物理等价性。

不把文件数、符号数、工时或某次性能测量写成长期门槛。它们是某次测量的结果，不是判据；
当作门使用会在上游变动时给出错误的通过或失败。

## 8. 临时研究产物

一次性探针、编译对象、日志和性能输出放在仓库外的临时目录，结论被当前 Goal 吸收后立即
删除。它们不做冷归档、不保留压缩包，也不为已经结束的实验留下软链接。

外置卷只用于**仍在使用且可再生**的大型构建目录、编译缓存或只读源码克隆；位置通过本地
环境或构建参数提供，不写入仓库。主线测试不得依赖某个仓库外历史目录才能复跑。
